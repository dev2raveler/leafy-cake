# 레터링 케이크 주문 프로토타입 구현 체크리스트

[프로토타입 초안](../prototype-draft.md)을 기준으로 고객의 주문 요청부터 매장의 입금 확인과 픽업 완료까지 구현한다. 각 항목은 화면에서 동작을 확인한 뒤 체크한다.

## 범위와 기본값

- 단일 매장의 픽업 주문을 `apps/demo`에서 구현한다. 고객 화면은 모바일 우선으로, 매장 화면은 모바일과 데스크톱에 맞춰 구성한다.
- 상품, 픽업 일정, 예시 주문은 목업 데이터를 사용한다. 매장 담당자가 전액 입금 여부를 직접 표시한다. 회원가입, API, 실제 결제와 알림은 범위에서 제외한다.
- 주문과 상태 변경은 `localStorage`에 저장한다. 고객과 매장 화면을 같은 브라우저 프로필에서 오가며 시연한다.
- 레터링 문구, 주문자 이름과 연락처는 필수로 입력하고 추가 요청 사항은 선택으로 둔다.

## 1. 목업 데이터와 주문 상태 준비

- [x] `apps/demo`에 설치된 Next.js 문서에서 페이지 라우팅과 클라이언트 컴포넌트 지침을 확인한다.
- [x] 케이크별 썸네일과 상세 이미지, 이름, 설명, 기본 가격, 크기·맛 옵션 및 옵션별 추가 금액을 준비한다.
- [x] 상세 화면과 주문 확인에 같은 가격 계산을 사용한다. 총액은 기본 가격에 선택한 크기와 맛의 추가 금액을 합산한다.
- [x] 한국 시간 기준으로 날짜별 픽업 가능 시간대를 정의한다. 시연할 때 선택 가능한 날짜와 시간이 표시되는지 확인한다.
- [x] 주문번호, 케이크와 선택 옵션, 요청 시점의 총액, 픽업 일시, 레터링 문구, 추가 요청, 이름과 연락처, 입금 확인 여부, 주문 상태, 거절 사유를 주문 데이터에 담는다.
- [x] 매장 목록에서 여러 상태를 살펴볼 수 있도록 예시 주문을 준비한다. 이후 제출과 상태 변경은 고객·매장 화면이 공유하는 주문 저장 로직을 사용한다.

가격 계산, 날짜별 시간대 표시, 주문 저장은 검증용 화면에서 확인했다. 고객과 매장 화면 연결은 2절과 3절에서 진행한다.

## 2. 고객 주문 화면

- [x] 케이크 목록에 썸네일, 이름, 가격을 표시하고 상세 화면으로 이동할 수 있게 한다.
- [x] 상세 화면에 큰 이미지, 이름, 설명, 크기·맛 옵션과 `주문하기` 버튼을 배치한다. 옵션을 바꾸면 총액을 즉시 갱신한다.
- [x] `주문하기`를 누르면 하단 드로어를 열고, 첫 단계에 픽업 가능 날짜를 고르는 달력을 표시한다. 기존 `@workspace/ui`의 드로어, 달력, 입력 컴포넌트를 재사용한다.
- [x] 날짜를 선택하면 해당 날짜의 시간대를 보여준다. 날짜를 바꾸면 이전 시간 선택을 초기화하고, 유효한 시간을 선택하면 `다음`을 활성화한다.
- [x] 두 번째 단계에 레터링 문구, 추가 요청 사항, 이름, 연락처 입력란을 배치한다. 필수 항목이 유효하면 `완료`를 활성화한다.
- [x] `완료`를 누르면 드로어를 닫고 주문 확인 화면에 케이크, 옵션, 총액, 픽업 일시, 레터링 및 주문자 정보를 표시한다. 내용을 수정하러 돌아가면 기존 입력값을 유지한다.
- [x] 주문 요청을 보내면 고유한 주문번호를 발급하고 **접수 대기** 상태로 저장한다. 제출 버튼을 연속으로 눌러도 주문은 한 건만 생성되도록 한다.
- [x] 접수 화면을 주문번호별 상태 화면으로 재사용한다. 주문번호와 현재 상태를 표시하고, 알 수 없는 주문번호로 접근했을 때 안내를 보여준다.

## 3. 매장 주문 관리 화면

- [x] 주문 목록을 모바일에서는 카드, 데스크톱에서는 표로 표시한다. 두 화면에서 주문번호, 픽업 일정, 상태를 확인하고 주문 상세를 열 수 있게 한다.
- [x] 주문 상세에 케이크 디자인, 선택 옵션, 총액, 픽업 일시, 레터링 문구, 추가 요청, 고객 이름과 연락처를 표시한다.
- [x] **접수 대기** 주문에 전액 입금 확인과 주문 확정 동작을 제공한다. 입금 확인 후에 `주문 확정`을 활성화한다.
- [x] **주문 확정 → 제작 중 → 픽업 준비 → 픽업 완료** 순서대로 진행할 수 있게 한다. 현재 상태에서 할 수 있는 동작을 표시한다.
- [x] **접수 대기** 주문을 거절할 때 사유를 필수로 입력받는다. 거절한 주문은 **접수 거절**로 저장하고 사유를 매장 상세 화면에 표시한다.
- [x] 상태 변경을 저장하고, 매장 목록과 고객의 주문 상태 화면에 같은 주문 상태를 표시한다.

## 4. 시연 및 검증

- [x] **정상 주문**을 모바일 너비에서 제출한다. 옵션 변경에 따른 가격 갱신, 날짜 변경 시 시간 초기화, 필수 항목에 따른 버튼 활성화, 수정 화면에서의 입력값 유지, 중복 제출 방지를 확인한다.
- [x] **매장 처리**를 시연한다. 방금 제출한 주문을 매장 목록에서 열어 입금 확인 전에는 확정할 수 없는지 확인하고, 입금 확인 후 픽업 완료까지 진행한다. 고객 화면을 다시 열 때 단계별 상태가 일치하는지 확인한다.
- [x] **접수 거절**을 별도 주문으로 시연한다. 사유가 비어 있으면 거절이 막히는지, 사유를 기록하면 고객 화면에 **접수 거절**이 표시되는지 확인한다.
- [x] **저장 복원**을 검증한다. 고객과 매장 화면을 새로고침한 뒤에도 새 주문과 변경된 상태가 유지되는지 확인한다.
- [x] 모바일 너비의 고객·매장 화면과 데스크톱 너비의 매장 화면에서 입력, 목록 조회, 상태 변경이 가능한지 확인한다.
- [x] `pnpm --filter demo lint`를 실행한다.
- [x] `pnpm --filter demo typecheck`를 실행한다.
- [ ] `pnpm --filter demo build`를 실행한다.

2026년 11월 24일에 Chromium의 같은 브라우저 세션에서 검증했다. 모바일(390×844)에서 주문을 제출하고 매장 카드 목록을 통해 픽업 완료까지 처리했다. 옵션에 따라 총액이 32,000원에서 40,000원, 43,000원으로 갱신됐고, 제출 버튼을 연속으로 눌렀을 때 주문이 한 건만 저장됐다. 데스크톱(1440×900)에서는 매장 표에서 별도 주문을 열고, 빈 사유와 공백만 입력한 사유가 거절을 막는지 확인한 뒤 사유를 입력해 거절했다. 새로고침 후 고객과 매장 화면에서 두 주문의 최종 상태가 유지됐으며, 거절 사유도 매장 상세에서 다시 확인했다.

기본 빌드는 이 실행 환경에서 Turbopack이 내부 포트를 열 때 `Operation not permitted (os error 1)`로 실패했다. `pnpm --filter demo build --webpack`은 통과했으며, 이 빌드를 `pnpm --filter demo start`로 실행해 위 시연을 진행했다.
